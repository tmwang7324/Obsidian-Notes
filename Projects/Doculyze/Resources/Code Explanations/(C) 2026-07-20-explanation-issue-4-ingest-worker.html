Background

If you're new to the project: what exists before this commit

DocuLyze lets a user drag a PDF (or Word doc, or text file) into the browser, and the goal — eventually — is to let them chat with it. Before that can happen, the file has to get from the user's disk into cloud storage, get recorded in a database, and then get read: its text extracted so it can later be chunked and embedded for retrieval. This commit is about that middle step — getting a file from "safely stored" to "someone (or something) has actually opened it and pulled the text out."

Two pieces of infrastructure were already in place before this commit landed:

1
Presigned-URL upload
The browser never sends the file through the Next.js server — server actions can't handle multi-megabyte bodies well. Instead, a server action mints a short-lived signed URL pointing at a specific spot in Google Cloud Storage (GCS), and the browser PUTs the bytes there directly.
2
Record-after-upload
finalizeUpload (in doculyze/app/actions/document/upload_document.tsx) runs after the browser's PUT finishes. It re-checks the object actually landed in GCS, cross-checks its size against what the client claimed, and only then writes a Firestore record with status: "uploaded". If bytes never made it, no record is ever created for them.

Every document record lives at a Firestore path that's generated by exactly one formula, defined once in _lib/database.tsx:

documentStoragePath(uid, docId) === "users/{uid}/documents/{docId}"

This matters a lot for what follows: the formula gets re-implemented a second time, in Python, inside the worker — and the codebase is deliberate about there only ever being one shape for this path, checked by every caller.

Before this commit, a document's Firestore status field could already technically hold the values "processing", "ready", or "failed" — they were declared in the DocStatus type — but nothing in the code ever produced them. A document landed at "uploaded" and stayed there forever. This commit is what makes the next three statuses reachable (well, two of them — "ready" is explicitly left for a future ticket, #5).

If message queues are new to you

A message queue (here, RabbitMQ) is a small, separate service that sits between two programs that don't want to talk to each other directly. A producer drops a small message onto a named queue; a consumer, running as its own separate process (possibly on a separate machine), reads messages off that queue one at a time and does something with them. Neither side needs to know the other is even running at that moment — RabbitMQ holds the message until someone's ready for it. That's the whole appeal here: the web server that handles uploads should never have to wait around for a PDF to be parsed, and the parser shouldn't need to know anything about HTTP requests or browsers.

If "sandboxing a subprocess" is new to you

Parsing a PDF means running someone else's library code (pypdf) against bytes a stranger uploaded. Malformed or adversarial files are a known way to crash a parser or make it hang forever (imagine a PDF crafted to trigger an infinite loop). The fix used here is to run the actual parsing in a child process, with a hard timeout. If that child process crashes, hangs, or misbehaves, the parent process (the one actually consuming from RabbitMQ) is completely unaffected — it just sees "that subprocess didn't return in time" and moves on to the next message.

The narrow background: what this ticket had to decide

The GitHub issue's implementation guide (authored collaboratively, then revised after what the repo calls a "grill" — a maintainer interrogation session) frames the ticket tightly: a successful finalizeUpload should publish exactly one small message, an "envelope," and an always-on Python worker should consume it, claim the document, download it, sanity-check it, parse it, and land it at either processing or failed. Getting all the way to ready — the state where the doc is actually usable for chat — is explicitly out of scope; parsed text is discarded at the end of this pipeline, held in memory just long enough to log its length.

That narrowness is the point: this is a "tracer" ticket. It proves the pipe works end-to-end — enqueue, consume, claim, download, verify, parse — before the next ticket (#5) worries about persisting anything.

Intuition

The claim-ticket model

Here's the idea that makes the whole design click into place: the message that travels through RabbitMQ never contains the file, or even a copy of its metadata. It's just two strings:

{ "uid": "abc123", "docId": "doc-9f2e" }

Think of it like a coat-check ticket. You don't hand the attendant your coat every time you want to ask "is my coat ready?" — you hand them a numbered ticket, and they go look up the coat on their own rack using that number. Here, the "rack" is Firestore (for status and metadata) and GCS (for the actual bytes). The worker, on receiving the ticket, re-reads everything it needs itself. This has a lovely side effect: the envelope can never disagree with the record, because it doesn't carry a competing copy of anything. If the record's content type changed between publish and consume, the worker sees the current truth, not a stale echo.

Two independent programs, in two different languages, agree on very little: a queue name, a two-field JSON shape, and that one path formula. That's deliberate — it's what lets either side be replaced later (the repo's ADR-0001 calls this out: a broker swap should only touch the "thin publish/consume shells").

What could go wrong, and how each piece answers it

Almost everything interesting in this commit is a defense against one specific failure mode. It's worth walking through them as a table before diving into code, because the code will make a lot more sense once you know why each piece exists.

What could go wrongHow it's handled
RabbitMQ is down, or RABBITMQ_URL isn't set (e.g. a dev running npm run dev without Docker) The publish happens in its own try/catch, after the Firestore write already succeeded. A failure is logged, never thrown — the user's upload still succeeds, and the doc simply rests at "uploaded" instead of progressing. ("Swallow-and-log.")
The RabbitMQ connection drops mid-session (broker restart, network blip) The producer doesn't keep a single connection open forever and hope for the best. It lazily connects on first use, and both the connection and channel wire up error/close listeners that null out the cache — so the very next publish transparently reconnects.
A message looks "sent" but the broker never actually durably received it (buffer wrote locally, connection died before the frame arrived) Publishing uses a confirm channel and awaits the broker's acknowledgement (with a 5-second timeout) before treating the publish as successful.
The worker crashes after claiming a document but before finishing parsing it RabbitMQ redelivers the unacked message. The claim logic sees the doc already sitting at "processing" and issues a guarded RERUN rather than either duplicating the claim or refusing to reprocess.
Two workers (or a crash-and-redeliver race) try to claim the same document at once The claim read-and-write happens inside a single Firestore transaction, so only one caller can win the uploaded → processing transition.
Someone renames a .exe to .pdf and uploads it (or the extension otherwise lies) A dependency-free magic-number precheck inspects the first few bytes against the content type stored on the Firestore record, before any parser ever touches the file.
A file passes the byte-signature check but is still malformed enough to crash or hang a parser Parsing runs in a subprocess with a timeout (20s default). A crash or hang there surfaces as a caught error in the parent, never a dead worker process.
A manually-replayed message (from the dead-letter queue) accidentally lands on a document that already finished successfully or already failed The claim function treats ready/failed as terminal — it returns SKIP and does nothing. Status never regresses.
Something genuinely broke — bad JSON, Firestore unreachable, an unhandled bug The consumer nacks (rejects, no requeue), which routes the message to a dead-letter queue for a human to look at. This is different from a "the file was bad" outcome, which is acked normally.

What the user actually sees (for now)

This ticket is backend-only — the commit message says as much (TODO: I haven't set up proper visual confirmation of parse success on the frontend). A document uploaded through this pipeline will, from Firestore's point of view, walk through pending → uploaded → processing, and then either stay at processing (success, for now — ready is ticket #5) or drop to failed. But at the time of this commit, the UI has no live view into that. A later commit (issue #10, already visible in this repo's current working tree) adds a Server-Sent-Events stream so the upload page can show live status — but that's a separate piece of work layered on top of this one.

Code walkthrough

The commit touches 32 files across three areas: a new Python package (ingest-worker/), two new TypeScript modules plus a small edit to the existing finalizeUpload, and infrastructure (Docker Compose, an emulator config tweak). I'll walk through it roughly in the order a message actually flows: producer, then worker skeleton, then the worker's internal pipeline stage by stage, then how it all gets run and tested.

Node.jsThe producer: two files, one job

The producer side splits cleanly into two modules with different jobs: _lib/rabbitmq.ts owns the connection's lifecycle, and _lib/ingest_broker.ts owns the actual publish call. Splitting these matters because the lifecycle logic (reconnects, topology declaration) is exactly the kind of thing you want isolated and unit-testable in one place, separate from "what message am I sending right now."

_lib/rabbitmq.ts — connection lifecycle

The key function is createChannel(). Read its shape carefully — the comments in the source are unusually explicit about why, because this replaced an earlier, buggier version (more on that below):

let channelPromise: Promise<amqp.ConfirmChannel> | null = null;

export function createChannel(): Promise<amqp.ConfirmChannel | null> {
  const url = process.env.RABBITMQ_URL;
  if (!url) {
    if (!warnedDisabled) {
      console.info("RABBITMQ_URL unset — ingest disabled; uploads rest at 'uploaded'.");
      warnedDisabled = true;
    }
    return Promise.resolve(null);
  }
  if (!channelPromise) {
    channelPromise = connect(url).catch((err) => {
      channelPromise = null; // don't cache a rejected promise; next call retries
      throw err;
    });
  }
  return channelPromise;
}

A few things worth noticing:

  • No RABBITMQ_URL means "ingest disabled," not an error. A developer running npm run dev without Docker running gets exactly one quiet console.info, not a stack trace on every upload.
  • It caches the in-flight promise, not the resolved channel. The function itself is deliberately not async — the comment in the source calls this out directly: assigning channelPromise = connect(url) happens synchronously, before any await. That's what makes two uploads landing in the same tick share exactly one connection attempt instead of racing to open two.
  • Failure un-caches itself. If connect() rejects, the .catch nulls channelPromise before rethrowing — so a failed connection attempt isn't permanently remembered as "the" cached result; the next publish gets a fresh try.

Inside connect(), two details matter a lot more than they look:

const conn = await amqp.connect(url);
// Attach BEFORE createConfirmChannel + the asserts: if the connection drops with
// no listener attached, Node re-throws the 'error' event and crashes the process.
conn.on("error", invalidate);
conn.on("close", invalidate);
const ch = await conn.createConfirmChannel();
ch.on("error", invalidate);
ch.on("close", invalidate);

First: createConfirmChannel(), not the plain createChannel(). A confirm channel is the piece that lets the producer later await proof that RabbitMQ durably received a message, rather than just trusting a local write buffer. Second: the error/close listeners exist for a very concrete reason spelled out in the comment — Node.js treats an EventEmitter's unhandled error event as fatal and crashes the whole process. Attaching a no-op-ish handler here (it just invalidates the cache) is not defensive paranoia; skip it and a broker restart takes down the Next.js server.

This was a deliberate revision

The GitHub issue thread includes a follow-up comment, dated the day before this commit, titled "Producer hardening." It explains that an earlier version of this code opened one connection eagerly at module load (via top-level await) and cached the resolved channel — which meant that after the first broker restart, ingest was silently, permanently broken until someone restarted the whole Next.js server. The lazy-promise-cache-plus-reconnect design you're reading here is the fix, arrived at through exactly the kind of "what happens when X restarts" interrogation the repo calls a design grill.

The same connect() function also declares the message topology — the queue, the dead-letter exchange, the dead-letter queue — every time it (re)connects:

await ch.assertExchange(DLX, "direct", { durable: true });
await ch.assertQueue(DEAD_QUEUE, { durable: true });
await ch.bindQueue(DEAD_QUEUE, DLX, QUEUE);
await ch.assertQueue(QUEUE, {
  durable: true,
  arguments: { "x-dead-letter-exchange": DLX },
});

assertQueue/assertExchange are idempotent declarations — "make sure this exists with these properties," not "create, and fail if it's already there." The comment above this block flags something clever: RabbitMQ hard-fails an assertQueue call if the queue already exists with different arguments. That's used on purpose as a drift alarm — if the Node producer and the Python consumer (which declares the identical topology independently) ever disagree about the dead-letter-exchange argument, the mismatch surfaces immediately as a connection error instead of silently routing messages nowhere.

_lib/ingest_broker.ts — the publish itself

This is the module that finalizeUpload actually calls. Its whole job is publishIngestJob(uid, docId):

export async function publishIngestJob(uid: string, docId: string): Promise<void> {
  const ch = await createChannel();
  if (!ch) return; // ingest disabled (RABBITMQ_URL unset) — doc rests at `uploaded`.

  const body = Buffer.from(JSON.stringify({ uid, docId }));

  await new Promise<void>((resolve, reject) => {
    const timer = setTimeout(
      () => reject(new Error("ingest publish confirm timed out")),
      CONFIRM_TIMEOUT_MS,
    );
    ch.sendToQueue(
      QUEUE,
      body,
      { persistent: true, contentType: "application/json" },
      (err) => {
        clearTimeout(timer);
        if (err) reject(err);
        else resolve();
      },
    );
  });
  console.log("Ingest job published (confirmed) for", uid, docId);
}

The interesting bit is that fourth argument to sendToQueue — a callback. That's the confirm-channel API: instead of trusting the boolean that plain sendToQueue returns (which only tells you the message was accepted into amqplib's local write buffer, not that RabbitMQ received it), this callback fires only once the broker has durably written the persistent message to the durable queue. The whole thing is wrapped in a Promise with a manual 5-second timeout, so a stalled broker can't hang the user's upload request forever — it just times out and gets treated as an unknown outcome.

Wiring it into finalizeUpload

Here's the actual integration point, in app/actions/document/upload_document.tsx. This is the single most important few lines in the whole ticket, because it's where the "never fail the user's upload over a broker problem" decision gets enforced structurally, not just by convention:

        await finalizeDocumentRecord({ docId, file_name: fileName, title, contentType: contentType, size: actualSize, status: "uploaded" });
        revalidatePath('/dashboard');
    } catch (error) {
        console.error("Error finalizing upload:", error);
        throw error;
    }
    // Flip-then-publish, swallow-and-log (GRILL 2026-07-18): the record is already
    // `uploaded`, so a broker outage must never surface as a failed upload — the
    // doc is visibly stuck-but-recoverable, not lost. Hence this sits OUTSIDE the
    // rethrowing catch above, in its own. Re-publish sweep is out of scope (#9 sibling).
    try {
        await publishIngestJob(uid, docId);
    } catch (err) {
        console.error("ingest enqueue failed; doc stuck at uploaded:", docId, err);
    }
}

Notice the shape: there are two separate try/catch blocks stacked back to back, not one. The first one (already existing before this commit) wraps the Storage verification and the Firestore write, and it rethrows — a genuine upload problem (size mismatch, missing object) should fail loudly. The second, new one wraps only the publish, and it does not rethrow — it just logs. "Flip-then-publish" names the ordering: the Firestore flip to uploaded has to happen and fully succeed first; only then is the (best-effort) publish attempted. If the publish fails, the function still returns normally, and the document simply sits at uploaded — a state the codebase considers "visibly stuck, but recoverable," not lost. (An automatic sweep to recover such stuck documents is explicitly deferred to a future ticket, #9.)

Also worth a small note: the size-mismatch branch, a few lines above, writes status: "failed" and then throws — which means it exits through the first catch block and never reaches the publish call at all. A failed finalize publishes nothing, by construction of the control flow, not by an explicit check.

def document_storage_path(uid: str, doc_id: str) -> str:

"4th caller" is a comment worth pausing on — it's counting call sites of a formula that intentionally exists in exactly one conceptual place (the signer, the finalize-time verify, the Firestore record writer, and now this) even though, because it crosses a language boundary, it has to be physically duplicated as literal Python. The discipline is: never derive this path any other way, anywhere.

PythonThe claim: guarded status transitions

firestore_status.py is where the "what if this message gets delivered twice" question gets answered. It exposes one function, claim_for_processing, that returns one of four outcomes:

class Claim(Enum):
    CLAIMED = "claimed"  # uploaded -> processing, proceed to parse
    RERUN = "rerun"      # already processing (crash-after-claim redelivery) -> re-parse
    SKIP = "skip"        # ready/failed -> ack, no-op (no regression)
    ABSENT = "absent"    # pending or missing -> log warning, ack

And the transaction that decides between them:

@firestore.transactional
def txn(tx) -> Claim:
    snap = ref.get(transaction=tx)
    if not snap.exists:
        return Claim.ABSENT
    status = snap.get("status")
    if status == "uploaded":
        tx.update(ref, {"status": "processing", "claimedAt": firestore.SERVER_TIMESTAMP})
        return Claim.CLAIMED
    if status == "processing":
        tx.update(ref, {"claimedAt": firestore.SERVER_TIMESTAMP})
        return Claim.RERUN
    if status in ("ready", "failed"):
        return Claim.SKIP
    return Claim.ABSENT  # "pending" or unknown

The whole read-check-write sequence happens inside a Firestore transaction — not a plain read followed by a separate write. That matters because a transaction is what actually prevents two concurrent callers from both seeing "uploaded" and both believing they won the claim; Firestore serializes the transactions so only one succeeds in flipping the status, and a genuinely concurrent second attempt would retry and see the now-updated status. With a single consumer at prefetch 1 (more on that below) this contention is mostly theoretical today — but the code is written so it stays correct the day a second worker process joins.

The RERUN branch deserves a second look, because the obvious-seeming alternative — "if it's already processing, just skip it, someone's already on it" — is exactly what this code doesn't do. If the worker died mid-parse last time, nobody is "already on it" anymore; the document would be stuck at processing forever if redelivery were treated as a no-op. So RERUN deliberately re-runs the whole pipeline — download, precheck, parse — again. It's safe to do so because the only side effect any of this produces (this ticket) is the status write itself, which is naturally idempotent.

Compare that to SKIP: once a document reaches ready or failed, those are treated as terminal. This is what makes it safe to manually replay a message from the dead-letter queue during debugging — worst case, it lands on an already-resolved document and does nothing, because SKIP never regresses a terminal status back to processing.

PythonThe job entry: run_ingest_job

job.py is the function that ties everything together — and it's deliberately written to know nothing about RabbitMQ at all. Compare its signature to what actually gets consumed off the queue: it just takes a plain dict.

def run_ingest_job(envelope: dict) -> None:
    uid, doc_id = envelope["uid"], envelope["docId"]
    db = firestore_client()

    decision = claim_for_processing(db, uid, doc_id)
    if decision in (Claim.SKIP, Claim.ABSENT):
        return

    snap = db.collection("users").document(uid).collection("documents").document(doc_id).get()
    content_type = snap.get("contentType")
    data = storage_bucket().blob(document_storage_path(uid, doc_id)).download_as_bytes()

    if not precheck(content_type, data):
        mark_failed(db, uid, doc_id)
        return

    try:
        text = run_parser_sandboxed(parser_for(content_type), data)
    except ParseError as exc:
        mark_failed(db, uid, doc_id)
        return

    log.info("parsed %s/%s: %d chars (held in memory only)", uid, doc_id, len(text))

This is explicitly called out in the design doc as "the broker-free seam" — run_ingest_job takes an envelope-shaped dict and talks only to Firestore and Storage, never to pika or RabbitMQ. That's a testability decision as much as an architectural one: the test suite (which we'll get to) drives this function directly, seeding Firestore and Storage state by hand and calling it with a plain dict, with zero broker involved.

Follow the control flow and you can see the whole "two gates" idea play out in code: claim first (do I even own this document right now?), then download, then precheck (do the bytes match what they claim to be?), then — only if that passes — the actual parse. Each gate that fails calls mark_failed and returns early; nothing after a failed gate ever runs. And notice what's absent: there's no status = "ready" anywhere. A successful parse just logs the character count and returns. The comment is explicit that persisting the text and flipping to ready is deliberately somebody else's ticket.

PythonThe precheck: don't trust the extension

precheck.py is intentionally dependency-free — no third-party library, just raw byte comparisons and the Python standard library's built-in zipfile module. The idea: every file format has a recognizable "magic number" at the start of its bytes, and a five-line PDF that's actually a renamed shell script won't have one.

PDF_MAGIC = b"%PDF-"
ZIP_MAGIC = b"PK\x03\x04"
CFB_MAGIC = b"\xd0\xcf\x11\xe0\xa1\xb1\x1a\xe1"

def precheck(content_type: str, data: bytes) -> bool:
    if content_type == "application/pdf":
        return data.startswith(PDF_MAGIC)
    if content_type == DOCX_TYPE:
        return data.startswith(ZIP_MAGIC) and _zip_has_entry(data, "[Content_Types].xml")
    if content_type == "application/msword":
        return data.startswith(CFB_MAGIC)
    if content_type in TEXT_FAMILY:
        if any(data.startswith(sig) for sig in BINARY_SIGS):
            return False
        if b"\x00" in data:
            return False
        try:
            data.decode("utf-8")
        except UnicodeDecodeError:
            return False
        return True
    return False

Two details are worth flagging. First, .docx gets an extra check beyond just "starts with the ZIP magic bytes" — .docx files are literally ZIP archives, so the code also opens the ZIP's central directory and checks it contains a [Content_Types].xml entry, which is specific to the Office Open XML format rather than any old ZIP. Second, the "text family" branch (plain text, JSON, Markdown, etc.) is checked by exclusion: does it start with any known binary signature (meaning something binary is masquerading as text), does it contain a NUL byte, and does it decode cleanly as UTF-8? Fail any of those and it's rejected.

There's an accepted, documented gap here: .doc (legacy Word) shares its CFB (Compound File Binary) signature with several other old Microsoft formats — .xls, .ppt. A spreadsheet renamed to .doc will sail through this precheck. That's fine, by design — it's caught one layer later, when antiword (the actual .doc parser) chokes on it and the parse itself fails. The precheck's job is to reject the cheap, obvious mismatches before spending a subprocess spin-up on them; it was never meant to be the only line of defense.

PythonParsing inside a sandbox

This is three small files working together: parsers.py (what to run), sandbox.py (how to run it safely), and parse_entry.py (the actual child-process entry point).

sandbox.py's run_parser_sandboxed is the one that matters most conceptually — it launches an entirely separate Python process (via subprocess.run, invoking python -m ingest.parse_entry <parser_name>), feeds it the raw bytes on stdin, and waits for text back on stdout, all bounded by a timeout:

try:
    proc = subprocess.run(
        [sys.executable, "-m", "ingest.parse_entry", parser_name],
        input=object_bytes,
        capture_output=True,
        timeout=timeout_s,
        env=_child_env(),
    )
except subprocess.TimeoutExpired as exc:
    raise ParseError(f"{parser_name} timed out after {timeout_s}s") from exc
if proc.returncode != 0:
    raise ParseError(f"{parser_name} exited {proc.returncode}: ...")
return proc.stdout.decode("utf-8", errors="replace")

The child, parse_entry.py, is deliberately dumb — it reads bytes off stdin, tries exactly one parser function, and on any exception at all, prints an error to stderr and exits with a non-zero code:

try:
    text = PARSERS[parser_name](data)
except Exception as exc:
    print(f"parse failed ({parser_name}): {exc}", file=sys.stderr)
    return 1

Put together: whatever goes wrong inside the actual parsing library — a crash, an infinite loop, a stack overflow — either shows up to the parent as a non-zero exit code, or (if it hangs) gets killed off by the timeout_s bound and surfaces as a TimeoutExpired. Either way, the parent process — the one holding the RabbitMQ connection and consuming the next message — never sees anything worse than a caught ParseError exception. This is the literal meaning of "sandboxed": the untrusted work happens somewhere that can die without taking anything else down with it.

parsers.py is the dispatch table plus the actual extraction logic — pypdf for PDFs, python-docx for .docx, plain UTF-8 decoding for text files, and antiword (a system binary, invoked via subprocess) for legacy .doc. That last one has a fun wrinkle: antiword only knows how to read a file path, not stdin, so the .doc branch has to write its bytes to a temp file first — but this temp file exists only inside the already-sandboxed child process, and gets cleaned up in a finally block:

def _parse_doc(data: bytes) -> str:
    tmp = tempfile.NamedTemporaryFile(suffix=".doc", delete=False)
    try:
        tmp.write(data)
        tmp.close()
        proc = subprocess.run(["antiword", tmp.name], capture_output=True)
        if proc.returncode != 0:
            raise RuntimeError(f"antiword exited {proc.returncode}: {proc.stderr[:200]!r}")
        return proc.stdout.decode("utf-8", errors="replace")
    finally:
        os.unlink(tmp.name)

PythonThe consumer shell: ack, nack, DLQ

consumer.py is explicitly labeled in its own docstring as "the ONLY broker-aware module" — every other Python file in this package could, in principle, be reused with a completely different message broker, or no broker at all (as the tests demonstrate). Its core is short:

def on_message(channel, method, properties, body) -> None:
    try:
        envelope = json.loads(body)
        run_ingest_job(envelope)
        channel.basic_ack(delivery_tag=method.delivery_tag)
    except Exception:
        log.exception("infra failure; dead-lettering delivery")
        channel.basic_nack(delivery_tag=method.delivery_tag, requeue=False)

channel.basic_qos(prefetch_count=1)
channel.basic_consume(queue=queue, on_message_callback=on_message, auto_ack=False)

This is where the "ack vs. nack" distinction — probably the single most important policy decision in the whole ticket — actually gets enforced. Read it carefully: run_ingest_job itself never raises for a document that's simply bad (wrong bytes, corrupt PDF, whatever) — it catches those cases internally and writes status: "failed". Because of that, the try block above completes normally for a bad file too, and it gets basic_ack'd just like a good one. The except branch only fires for something the code didn't expect at all: malformed JSON, Firestore or Storage being unreachable, a genuine bug. Those get basic_nack'd with requeue=False, which RabbitMQ's topology routes straight to the doc.ingest.dead queue via the dead-letter exchange declared earlier.

Why this distinction matters

It means the dead-letter queue's depth is a pure malfunction alarm. If you see messages piling up in doc.ingest.dead, that never means "a user uploaded a bad PDF" — failed-status documents don't go there at all, they're acked normally and just sit in Firestore as failed. A dead-lettered message specifically means the worker or its infrastructure broke. That's a deliberate signal-to-noise decision: you don't want to page anyone over a user's corrupt upload, but you absolutely want to know if Firestore became unreachable.

The other line worth noticing is channel.basic_qos(prefetch_count=1). Prefetch controls how many unacknowledged messages RabbitMQ will hand this consumer at once; setting it to 1 means the worker processes exactly one envelope at a time, fully, before RabbitMQ will give it another. Combined with manual acking, this is what makes the crash-recovery story work: if the worker process dies mid-job, that one message it was holding is simply never acked, so RabbitMQ eventually redelivers it — and, as covered above, the claim logic's RERUN path is exactly what's waiting to handle that redelivery correctly.

InfraDocker Compose and the dev-E2E wiring

The root-level docker-compose.yml defines two services: rabbitmq (the rabbitmq:4-management image, ports bound to 127.0.0.1 only — never exposed beyond localhost) and ingest-worker (built from the new ingest-worker/Dockerfile, with no ports: section at all — it's unreachable from outside the Docker network by construction, not just by convention). The worker service also mounts the Firebase service account credential file read-only rather than baking it into the image.

There's a small but genuinely tricky wrinkle solved by docker-compose.dev.yml (an override file, merged in only for local end-to-end testing) plus a one-line change to doculyze/firebase.json. During local development, the Next.js app writes to a Firestore emulator (bound to 127.0.0.1:8085 by default) while Storage stays real GCS — because signed-URL uploads don't work against the Storage emulator. But 127.0.0.1 means "loopback only" — from inside a Docker container, that's the container's own loopback interface, not the host machine's. A containerized worker trying to reach the host's emulator at 127.0.0.1:8085 would just fail to connect. So:

// doculyze/firebase.json
"firestore": { "host": "0.0.0.0", "port": 8085 },  // was just { "port": 8085 }
# docker-compose.dev.yml
services:
  ingest-worker:
    environment:
      FIRESTORE_EMULATOR_HOST: host.docker.internal:8085

Binding the emulator to 0.0.0.0 makes it listen on all network interfaces, not just loopback — reachable from Docker's internal virtual network adapter. host.docker.internal is Docker's built-in DNS name that resolves to the host machine from inside a container. The comment in the compose file is explicit that this wiring lives only in the override file, never in the base docker-compose.yml or baked into the image — the same built artifact points at real production Firestore in any other environment simply by omitting this override.

Node.js PythonThe two test seams

The ticket's design doc calls out two distinct "seams" — points in the system deliberately shaped to be testable in isolation — and this commit adds a test file for each.

Seam 1 (doculyze/tests/upload/ingest-enqueue.test.ts, vitest) tests finalizeUpload's enqueue behavior without any real broker, by mocking the whole ingest_broker module at the import boundary:

vi.mock("@/_lib/ingest_broker", () => ({ publishIngestJob: vi.fn() }));

With that fake in place, it asserts exactly the three behaviors this whole design was built around: a successful finalize calls publishIngestJob exactly once with (uid, docId); a size-mismatch finalize (which ends at status: "failed") calls it zero times; and — the one that directly proves the swallow-and-log policy — making the fake publish reject still lets finalizeUpload resolve normally, with the record still sitting at "uploaded".

Seam 2 (ingest-worker/tests/test_job.py, pytest, run against the real Firebase emulators) drives run_ingest_job directly — no broker, no consumer, no pika. Each test seeds a Firestore record and a Storage object by hand, calls run_ingest_job({"uid": ..., "docId": ...}), and asserts the resulting status:

def test_replaying_a_good_envelope_is_idempotent():
    env = stage(PDF, pdf_fixture())
    run_ingest_job(env)
    run_ingest_job(env)  # redelivery: RERUN, same terminal state, no extra records
    assert support.read_status(UID, DOC) == "processing"

That's the replay-safety guarantee from the claim logic, proven directly rather than just asserted in a comment. Other cases in the same file cover a good PDF (ends at processing), text-bytes-mislabeled-as-PDF (precheck rejects, object retained), a corrupt-but-magic-numbered PDF (precheck passes, sandboxed parse fails), each of the four parser branches, and the terminal-state SKIP/ABSENT cases. Between the two files, the whole envelope-to-status pipeline gets exercised without either language ever needing a real, running RabbitMQ broker to test against.

Quiz

Five questions, click an answer to see if you're right and why.

1. Why does the RabbitMQ envelope only carry { uid, docId } instead of also including the file's content type, size, or the parsed text itself?

  • Because RabbitMQ messages have a strict size limit that would reject anything larger.
  • Because the worker re-reads everything it needs from Firestore/Storage itself, so the envelope can never disagree with the current record — it's a pointer, not a snapshot.
  • Because JSON messages in RabbitMQ can only contain string fields, never numbers or nested objects.
  • Because the Python worker doesn't have permission to read Firestore directly.

2. RabbitMQ is completely down when a user finishes an upload. What happens?

  • The upload fails and the user sees an error — nothing gets written to Firestore.
  • The upload still succeeds and the Firestore record still ends at "uploaded"; the publish failure is caught and logged separately, never surfaced to the user.
  • The record is written with status: "failed" since ingest couldn't be triggered.
  • finalizeUpload retries the publish in a loop until it succeeds or the request times out.

3. A worker claims a document (uploaded → processing) and then crashes before finishing the parse. RabbitMQ redelivers the message. What does claim_for_processing return the second time, and why?

  • SKIP — the document is already processing, so nothing more needs to happen.
  • ABSENT — a crashed claim leaves the record in an unrecognized state.
  • RERUN — because nobody is actually still working on it (the claimant died), so the whole download/precheck/parse pipeline needs to run again; it's safe because the only side effect is the idempotent status write.
  • CLAIMED — the transaction doesn't distinguish a fresh claim from a redelivered one.

4. A malicious file has a perfectly valid %PDF- magic-number header but is crafted to make a PDF-parsing library hang forever. What actually stops the worker from hanging forever too?

  • The magic-number precheck in precheck.py catches it before parsing starts.
  • The parser runs in a separate subprocess via run_parser_sandboxed, which enforces a timeout (default 20s) and raises ParseError if the child doesn't return in time — the main worker process is unaffected.
  • RabbitMQ's own message TTL expires the delivery and requeues it automatically.
  • Firestore's transaction timeout aborts the claim after 20 seconds.

5. What's the actual difference between a message getting basic_ack'd versus basic_nack'd (to the dead-letter queue) in consumer.py?

  • Acked messages are for PDFs; nacked messages are for every other file type.
  • Acked means the document ended at processing; nacked means it ended at failed.
  • Acked covers any outcome run_ingest_job resolved on its own — including a bad file correctly marked failed. Nacked (dead-lettered) is reserved for things run_ingest_job couldn't handle at all: bad JSON, an unreachable Firestore/Storage, or an unexpected bug — a pure infrastructure-malfunction signal.
  • Acked messages are deleted immediately; nacked messages stay in doc.ingest forever for manual review.
