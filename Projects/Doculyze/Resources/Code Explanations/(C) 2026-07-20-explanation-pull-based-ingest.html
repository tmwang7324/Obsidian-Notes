Uploaded files no longer just sit there: teaching DocuLyze to notice its own documents

commit 1eb90738dcfa · Thomas Wang · Sun Jul 19 2026 · 32 files changed, 1314 insertions(+)  ·  issue #4, "pull-based ingest"

A RabbitMQ broker and a sandboxed Python worker arrive in one commit, and together they close a loop that has been open since the very first upload: a file lands in Storage, a Firestore record says uploaded — and then, until this commit, absolutely nothing happens next.

Background

Before this commit, DocuLyze could accept a document and forget about it in the same breath. That sounds worse than it is — the forgetting was deliberate, a placeholder for work not yet built — but it's the right place to start, because the commit we're studying exists entirely to fill that gap.

New to message queues and sandboxed workers? Start here (skip if you already know this).

Most web apps do work in the same request that asked for it: you click "save," the server saves, you get a response. That's fine when the work is fast. It falls apart when the work is slow or unreliable — parsing a PDF can take seconds, hang on a malformed file, or crash outright, and you don't want a user's upload button to sit there spinning while that happens, let alone have one bad PDF take down your whole server process.

The standard fix is a message queue: instead of doing the slow work inline, the web server writes a short note — "please process document 42" — onto a queue and returns immediately. A completely separate process, the worker, sits there pulling notes off the queue one at a time and doing the slow work at its own pace. If the worker crashes, the queue still has the note (or can be told to redeliver it); the web server never even notices. RabbitMQ is one of the most common pieces of software used to host such a queue — it durably stores messages, hands them to workers, and can track acknowledgments so a message isn't lost if a worker dies mid-job.

Two more terms worth knowing: a sandboxed subprocess means "run this risky code (like parsing an untrusted file) in a separate child process," so that if it crashes, hangs, or misbehaves, only that child dies — the parent process that spawned it keeps running and can just try the next job. A magic-number check (or "magic byte sniff") means peeking at the first few bytes of a file to see if they match a known file-format signature — real PDFs start with the literal bytes %PDF-, for instance — as a cheap way to catch files that are lying about what they are before you spend real effort trying to parse them.

What already existed: upload without a destination

DocuLyze's upload flow (built in earlier commits, and unchanged in spirit by this one) works like this: the browser asks the server for a signed URL, PUTs the file's bytes straight to Google Cloud Storage, and then calls the finalizeUpload server action, which checks the bytes really landed and writes a Firestore record. That record — a DocumentRecord in doculyze/_lib/database.tsx — has always carried a status field typed as:

export type DocStatus = "uploaded" | "processing" | "ready" | "failed" | "pending" | "";

Look closely at that list. "pending" and "uploaded" were reachable — the upload flow set them. But "processing", "ready", and the parse-triggered flavor of "failed" were pure fiction: types that existed in the code because someone had already sketched out the future lifecycle of a document, with nothing anywhere that could actually produce them. A document could get uploaded and just... rest at uploaded forever. This commit is what makes processing a real, observable state for the first time.

The one-formula rule

One convention from the upload work carries forward and matters a lot here: documentStoragePath(uid, docId) in _lib/database.tsx is the single place the path formula users/{uid}/documents/{docId} is allowed to live. Every piece of code that needs to find a document's bytes in Storage — the URL signer, the finalize-time existence check, and now, with this commit, a brand-new Python process — calls that same formula rather than reinventing it. The commit's ingest-worker/src/ingest/paths.py is explicit about being the fourth caller of that one formula, reimplemented (Python can't literally import a TypeScript function) but kept byte-for-byte identical in shape. That's the kind of detail that looks trivial until the two copies drift and documents silently stop being found.

What this commit is scoped to (and, just as importantly, what it isn't)

The implementation guide behind issue #4 draws the boundary tightly: a document that parses successfully should end this pipeline at processing, with its extracted text held only in memory and then discarded. Getting from processing to ready — actually persisting the parsed text, chunking it, embedding it — is explicitly ticket #5's job, not this one's. So don't go looking for a vector store or a "ready" transition in this diff; it isn't there on purpose. What is here is the plumbing that gets a document's bytes from "sitting in Storage, unexamined" to "downloaded, sniffed, and parsed by something," reliably and safely, with nothing lost if any single piece of that chain falls over.

Intuition

The core idea is small enough to say in one sentence: after a successful upload, the server actions drops a tiny note on a queue, and a completely separate, sandboxed process picks that note up and does the risky work. Everything else in this commit is making that one sentence trustworthy under failure.

The note, not the package

The single most important design choice is what goes into that note. It would be tempting to hand the worker everything it needs up front — filename, content type, size, maybe even the bytes themselves. This commit does the opposite: the envelope that crosses the broker is exactly two fields, nothing else.

{ "uid": "user-a", "docId": "aB3xQ9k2" }

Think of it like a coat-check ticket, not the coat. The ticket doesn't describe your coat's color or material — it's just a claim number. Whoever holds the ticket goes to the counter (Firestore) and asks "what do you have for this number?", and the counter is the only source of truth. If the ticket said "black coat, size L" directly, and someone swapped your coat in storage, the ticket would now be lying. By making the ticket a pure pointer, it can never disagree with the record — the worker always re-reads the real contentType from Firestore rather than trusting whatever the envelope might have claimed. This is called out explicitly in the code as "pointer-only," and it's why the consumer is written to tolerate — even ignore — extra unknown keys: the contract can only grow, never drift.

The whole trip, with example data

Here's the shape of one document's journey through the new pipeline, with a concrete (fictional) example threaded through it.

BrowserPUTs notes.pdf
finalizeUpload()→
Next.js actionflips status
publish→
doc.ingestdurable queue
consume→
Python workerclaim → sniff → parse

Envelope carried on the queue: {"uid":"user-a","docId":"aB3xQ9k2"} — never the PDF's bytes, never its filename.

Walking through it with that example doc:

  1. The browser has already PUT notes.pdf's bytes directly to Storage (that part predates this commit). finalizeUpload confirms the bytes exist, checks the size, and writes the Firestore record's status to uploaded.
  2. Only after that write succeeds, finalizeUpload calls publishIngestJob("user-a", "aB3xQ9k2"). This is the "flip-then-publish" rule you'll see mentioned repeatedly in the code comments: a record must already be safely uploaded before anything is published about it.
  3. The envelope lands, durably, on the doc.ingest queue. If nobody's listening yet, it just waits there — RabbitMQ persists it to disk because both the queue and the message are marked durable/persistent.
  4. The Python worker, which has been blocked waiting on that queue, receives the envelope, claims the document (flips Firestore from uploaded to processing inside a transaction), downloads the actual bytes from Storage at users/user-a/documents/aB3xQ9k2, magic-byte-checks them against the contentType Firestore says they should be, and — if that check passes — hands the bytes to a sandboxed pypdf subprocess to extract text.
  5. If everything above succeeds, the document simply stays at processing (with the extracted text sitting in the worker's memory, about to be thrown away) — that's the commit's designed stopping point. If the file is a corrupt PDF, or claims to be a PDF but is actually a `.txt` file, the worker marks it failed instead, and — importantly — never deletes the underlying object. A failed parse means "we couldn't read this," not "this file is gone."

What happens when things go wrong (this is most of the actual code)

A tracer bullet like this earns its complexity almost entirely from the failure paths, not the happy path. Three different "what if" questions each get their own small, deliberate answer:

What if the broker is unreachable, or not even configured? A plain npm run dev without Docker running must not error-storm on every single upload. If RABBITMQ_URL is unset, the producer never even attempts to connect — it logs one quiet informational line, once, and returns. If the broker is configured but happens to be down, the publish attempt fails, gets caught, and gets logged — but never re-thrown. Either way, the already-uploaded record is untouched. The user's upload still succeeds from their point of view; the document is just "stuck but recoverable," a state a future, separate sweep (ticket #9, explicitly out of scope here) is meant to reconcile later.
What if the worker crashes mid-parse, or the same envelope gets delivered twice? This is what the little Claim enum in firestore_status.py exists to answer. It's a state machine with exactly four outcomes for "I received an envelope for this docId — what should I do?":
uploaded → CLAIMED
processing → RERUN
ready → SKIP
failed → SKIP
pending / missing → ABSENT

Every branch is decided inside one Firestore transaction, so two workers racing the same envelope can never both get CLAIMED.

The interesting branch is RERUN: if a worker crashes after claiming a document (flipping it to processing) but before finishing the parse, the message was never acknowledged, so RabbitMQ redelivers it — maybe to the same worker after it restarts, maybe to another one. That redelivery finds the record already at processing and, rather than treating that as an error, just... reprocesses it from scratch. Nothing about this ticket's side effects are non-idempotent (the only Firestore write is the status field), so redoing the work is always safe. Contrast that with ready or failed: those are terminal, and a redelivered or manually-replayed envelope for either one is a pure no-op — the system refuses to regress a resolved document back into an earlier state.

What if the file itself is malicious, corrupt, or lying about its type? Two independent gates, in order. First, precheck.py looks at the first few bytes — does a file claiming to be application/pdf actually start with the bytes %PDF-? This is cheap and dependency-free, and it catches the "renamed a .txt to .pdf" case before any real parsing library ever touches the bytes. Second, even bytes that pass the magic-number check get handed to the actual parser (pypdf, python-docx, antiword) inside a separate subprocess with a hard 20-second timeout. A parser that segfaults, hangs forever on a decompression bomb, or throws some exotic exception can only take down that one disposable child process — the parent worker, still waiting on the queue for the next envelope, is never at risk.

Two matching blueprints that must never drift

One subtlety worth calling out explicitly: the "topology" of the queue — its name, its durability, its dead-letter routing — has to be declared identically by the Node producer and the Python consumer. RabbitMQ's assertQueue/queue_declare calls are written to hard-fail if two callers try to declare the same queue with different arguments. That's treated as a feature, not a bug — the code comments call it "the drift alarm we want." Rather than trusting two people (or two future edits) to keep a shared config file in sync by hand, the system is built so that an actual mismatch between the TypeScript and Python declarations blows up loudly at connect time instead of silently misbehaving.

Code walkthrough

The commit touches 32 files, but it decomposes cleanly into a handful of groups: the Docker infrastructure that wires broker and worker together, the two-file Node producer, and seven small, single-purpose Python modules on the consumer side — each with its own pytest file. We'll walk them roughly in the order data flows through them.

1. Infrastructure: docker-compose.yml + docker-compose.dev.yml

docker-compose.yml (new, repo root)

Two services on an internal bridge network called ingest. The RabbitMQ service binds its AMQP and management-UI ports to 127.0.0.1 only — reachable from the host machine, never from outside it. The worker service, by contrast, declares no ports: mapping at all — it is only reachable by anything else on the internal ingest network, which in practice means only RabbitMQ. Its only way to be triggered is a broker envelope; there is no HTTP endpoint, no exposed anything, for the outside world to hit.

ingest-worker:
  build: ./ingest-worker
  environment:
    RABBITMQ_URL: amqp://doculyze:${RABBITMQ_PASS:-devpass}@rabbitmq:5672
    ...
  volumes:
    - ./doculyze/serviceAccount.json:/run/secrets/serviceAccount.json:ro
  networks: [ingest]      # no `ports:` — internal only
  depends_on:
    rabbitmq:
      condition: service_healthy

Credentials arrive by a read-only volume mount, never baked into the image — the same discipline the rest of the repo already follows for serviceAccount.json.

docker-compose.dev.yml (new, repo root)

A companion override file solving a real local-development snag: npm run dev writes Firestore records to the emulator, but the containerized worker, by default, would talk to production Firestore and see every document as simply absent. This override redirects the worker's FIRESTORE_EMULATOR_HOST to host.docker.internal:8085 — the host machine's emulator, reached through Docker's internal DNS name for "the machine running this container." It's a separate file rather than baked into the base compose file specifically so that emulator wiring can never accidentally ship in a "real" deployment; you have to opt into it with an extra -f flag. A one-line change in doculyze/firebase.json makes this possible at all — the Firestore emulator has to bind 0.0.0.0 instead of the default loopback-only 127.0.0.1, or a container's connection (which arrives over a virtual network adapter, not loopback) simply can't reach it.

2. The Node producer: rabbitmq.ts and ingest_broker.ts

doculyze/_lib/rabbitmq.ts (new)

This file owns exactly one thing: a live, reusable connection to RabbitMQ. The design here is worth pausing on because it's easy to get subtly wrong. createChannel() is written as a plain (non-async) function on purpose:

export function createChannel(): Promise<amqp.ConfirmChannel | null> {
  const url = process.env.RABBITMQ_URL;
  if (!url) {
    if (!warnedDisabled) {
      console.info("RABBITMQ_URL unset — ingest disabled; uploads rest at 'uploaded'.");
      warnedDisabled = true;
    }
    return Promise.resolve(null);
  }
  if (!channelPromise) {
    channelPromise = connect(url).catch((err) => {
      channelPromise = null; // don't cache a rejected promise; next call retries
      throw err;
    });
  }
  return channelPromise;
}

Being synchronous up to the point where channelPromise gets assigned matters: if two uploads finalize in the same tick of the event loop, both calls see the freshly-assigned promise before either one has had a chance to await anything, so they share a single in-flight connection attempt instead of racing to open two. Note also what's cached: the promise, not the eventually-resolved channel. That distinction is what makes reconnection work — connect() attaches 'error' and 'close' listeners on both the connection and the channel that null out channelPromise the moment either one drops, so the very next publish attempt transparently reconnects rather than reusing a dead handle forever. (Those listeners aren't just cleanup — amqplib re-throws an unhandled 'error' event and crashes the Node process, so attaching them is load-bearing, not decorative.)

The channel it hands back is a confirm channel (createConfirmChannel()), not a plain one — the difference matters and shows up in the next file. connect() also declares the full queue topology (the durable doc.ingest queue, its dead-letter exchange, and the doc.ingest.dead queue behind it) every time it establishes a fresh connection, so the topology is always in place before any publish is attempted.

doculyze/_lib/ingest_broker.ts (new)

This is the file that actually gets called from the upload flow — one exported function, publishIngestJob(uid, docId). Its job is to turn "I have a channel" into "the broker has durably accepted this message," which is a stronger and more useful guarantee than it sounds:

await new Promise<void>((resolve, reject) => {
  const timer = setTimeout(
    () => reject(new Error("ingest publish confirm timed out")),
    CONFIRM_TIMEOUT_MS,
  );
  ch.sendToQueue(
    QUEUE,
    body,
    { persistent: true, contentType: "application/json" },
    (err) => {
      clearTimeout(timer);
      if (err) reject(err);
      else resolve();
    },
  );
});

A plain sendToQueue call on an ordinary channel returns a boolean about whether the local write buffer accepted the write — it says nothing about whether the broker actually received and durably stored the message. On a confirm channel, that trailing callback only fires once the broker itself has acknowledged a persistent message landed on the durable queue. The 5-second timeout wrapped around it exists so a stalled broker can never hang the user's browser mid-upload; past that window, the code treats the outcome as merely unknown rather than a hard failure, because the message may well have landed anyway — retrying blind here would risk a duplicate, and the code comments are explicit that recovering from an unknown outcome is the future sweep's job (issue #9), not this function's.

doculyze/app/actions/document/upload_document.tsx (modified)

The wiring into the existing upload action is deliberately narrow — one new import, and a small block appended after the function's existing try/catch, not inside it:

await finalizeDocumentRecord({ docId, ..., status: "uploaded" });
revalidatePath('/dashboard');
} catch (error) {
  console.error("Error finalizing upload:", error);
  throw error;
}
// Flip-then-publish, swallow-and-log ...
try {
  await publishIngestJob(uid, docId);
} catch (err) {
  console.error("ingest enqueue failed; doc stuck at uploaded:", docId, err);
}

Placement here is the whole point. The existing catch block rethrows — a genuine upload failure (missing object, size mismatch) must still surface as an error to the caller. The new catch block does the opposite: it swallows. By the time execution reaches the publish call, the Firestore record has already, successfully, been written as uploaded — so a broker hiccup at this point is purely an ingest-pipeline problem, never an upload problem, and the code is careful not to conflate the two. The commit also threads a new contentType parameter through finalizeUpload and the one call site in upload_form.tsx that invokes it — a small plumbing fix so the worker (and the Firestore record it reads) gets the server-resolved, trusted content type rather than re-deriving it a second time inside finalizeUpload.

ingest-worker/src/ingest/config.py (new)

All environment-variable reading and the one-time Firebase Admin SDK initialization live here. Nothing exciting on its own, except for one habit worth noting: the boot log prints which Firestore and which Storage bucket the process actually resolved —

log.info(

ingest-worker/src/ingest/paths.py (new)

Eight lines, and the whole point is that it's only eight lines:

def document_storage_path(uid: str, doc_id: str) -> str:
    """4th caller of the ONE canonical path formula. ..."""
    return f"users/{uid}/documents/{doc_id}"

This is the "one-formula rule" from the Background section, reimplemented in a second language because Python obviously can't import a TypeScript function. It has to be kept in lockstep with documentStoragePath() in _lib/database.tsx by convention and code review, not by the compiler — a real, accepted cost of a polyglot system, made as small as possible by keeping the duplicated logic to a single, trivial function.

4. Claim state machine: firestore_status.py

ingest-worker/src/ingest/firestore_status.py (new)

The Claim enum from the Intuition section is implemented as one @firestore.transactional function, claim_for_processing. Running the read and the conditional write inside a single Firestore transaction is what gives the "exactly one worker gets CLAIMED" guarantee — Firestore itself serializes any two transactions that touch the same document, so if two consumers raced to claim the same envelope, one transaction would automatically retry and see the already-updated processing status the second time through.

if status == "processing":
    # Guarded re-claim, not a read-only peek: keeps contention behavior
    # correct when consumers multiply.
    tx.update(ref, {"claimedAt": firestore.SERVER_TIMESTAMP})
    return Claim.RERUN

Note that even the "do nothing new" branches (RERUN) still perform a write — refreshing a claimedAt timestamp — rather than just reading and returning. With a single worker and prefetch 1 this is currently belt-and-suspenders, but it means a future multi-worker deployment inherits correct contention behavior without anyone having to revisit this function.

5. Magic-number precheck: precheck.py

ingest-worker/src/ingest/precheck.py (new)

Deliberately dependency-free — no third-party library, just raw byte comparisons and the Python standard library's zipfile module (since a .docx is, under the hood, a zip archive):

def precheck(content_type: str, data: bytes) -> bool:
    if content_type == "application/pdf":
        return data.startswith(PDF_MAGIC)
    if content_type == DOCX_TYPE:
        return data.startswith(ZIP_MAGIC) and _zip_has_entry(data, "[Content_Types].xml")
    if content_type == "application/msword":
        return data.startswith(CFB_MAGIC)
    if content_type in TEXT_FAMILY:
        if any(data.startswith(sig) for sig in BINARY_SIGS):
            return False
        if b"\x00" in data:
            return False
        try:
            data.decode("utf-8")
        except UnicodeDecodeError:
            return False
        return True
    return False  # unknown contentType never should have been signed

Each branch checks the bytes against the record's stored contentType — not a fresh re-sniff used to decide the allowlist, since that decision was already made once, correctly, back when the upload was first signed. For the text-family branch, three separate checks stack: it must not start with any of the known binary signatures (catching, say, a PDF renamed to .txt), it must not contain a NUL byte, and it must decode cleanly as UTF-8. The function's own docstring is candid about a known, accepted gap: the CFB signature checked for .doc is shared by every legacy Office format, so a .xls renamed to .doc sails through this check and only gets caught two steps later, when antiword itself rejects it.

6. Sandboxed parsing: parsers.py, sandbox.py, parse_entry.py

These three files split cleanly by responsibility: parsers.py knows how to extract text from each format; sandbox.py knows how to run that extraction safely; parse_entry.py is the tiny, disposable program that sandbox.py actually spawns.

ingest-worker/src/ingest/sandbox.py (new)

def run_parser_sandboxed(
    parser_name: str, object_bytes: bytes, timeout_s: float | None = None
) -> str:
    ...
    try:
        proc = subprocess.run(
            [sys.executable, "-m", "ingest.parse_entry", parser_name],
            input=object_bytes,
            capture_output=True,
            timeout=timeout_s,
            env=_child_env(),
        )
    except subprocess.TimeoutExpired as exc:
        raise ParseError(f"{parser_name} timed out after {timeout_s}s") from exc
    if proc.returncode != 0:
        raise ParseError(
            f"{parser_name} exited {proc.returncode}: {proc.stderr.decode('utf-8', 'replace')[:300]}"
        )
    return proc.stdout.decode("utf-8", errors="replace")

The untrusted bytes travel over the child's stdin, and extracted text comes back over its stdout — a narrow, well-understood interface between parent and child. A timeout (20 seconds by default, a config.py knob) turns a hang into a raised ParseError instead of a stuck worker; a non-zero exit code (any exception inside the child) does the same. Either way, the parent process — the one still holding the RabbitMQ connection and waiting for the next envelope — never blocks indefinitely and never dies alongside a bad file.

ingest-worker/src/ingest/parse_entry.py (new)

def main() -> int:
    parser_name = sys.argv[1]
    data = sys.stdin.buffer.read()
    try:
        text = PARSERS[parser_name](data)
    except Exception as exc:
        print(f"parse failed ({parser_name}): {exc}", file=sys.stderr)
        return 1
    sys.stdout.buffer.write(text.encode("utf-8"))
    return 0

This is the entire child program — read bytes, try to parse, print text or exit non-zero. Note the bare except Exception: inside this specific, disposable, sandboxed child, catching everything is exactly correct, because the whole point of this file's existence is to convert any possible failure mode of an untrusted parser into a single, uniform "exit 1" signal that sandbox.py already knows how to handle.

ingest-worker/src/ingest/parsers.py (new)

A lookup table from content type to parser name, plus the four actual extraction functions — pypdf for PDFs, python-docx for .docx, a plain .decode("utf-8") for the text family, and a small wrapper around the antiword command-line tool for legacy .doc files. The .doc case has its own small wrinkle, called out directly in the code: antiword reads a file path, not stdin, so that one branch writes the bytes to a temporary file first —

tmp = tempfile.NamedTemporaryFile(suffix=".doc", delete=False)
try:
    tmp.write(data)
    tmp.close()
    proc = subprocess.run(["antiword", tmp.name], capture_output=True)
    ...
finally:
    os.unlink(tmp.name)

— using delete=False plus a manual os.unlink in a finally block, because on Windows a file opened by NamedTemporaryFile can't be reopened by a second process while the first handle is still open. Since this whole function is already running inside the sandboxed child, the temp file's lifetime is naturally scoped to that child's lifetime too — it dies (is cleaned up) right alongside it.

7. Tying it together: job.py

ingest-worker/src/ingest/job.py (new)

This is the seam the implementation guide calls out as the most important one to get right — run_ingest_job(envelope) is a broker-free, pure function of (uid, docId) against Firestore and Storage, and it's what the tests drive directly, with no RabbitMQ involved at all:

def run_ingest_job(envelope: dict) -> None:
    uid, doc_id = envelope["uid"], envelope["docId"]
    db = firestore_client()

    decision = claim_for_processing(db, uid, doc_id)
    if decision in (Claim.SKIP, Claim.ABSENT):
        log.info("skip/absent for %s/%s: %s", uid, doc_id, decision.value)
        return
    # CLAIMED or RERUN: the record is now `processing`.

    snap = ...get()
    content_type = snap.get("contentType")
    data = storage_bucket().blob(document_storage_path(uid, doc_id)).download_as_bytes()

    if not precheck(content_type, data):
        log.warning("precheck rejected %s/%s (%s)", uid, doc_id, content_type)
        mark_failed(db, uid, doc_id)
        return

    try:
        text = run_parser_sandboxed(parser_for(content_type), data)
    except ParseError as exc:
        log.warning("parse failed for %s/%s: %s", uid, doc_id, exc)
        mark_failed(db, uid, doc_id)
        return

    log.info("parsed %s/%s: %d chars (held in memory only)", uid, doc_id, len(text))

Read top to bottom, this function is the pipeline from the Intuition diagram: claim, download, precheck, parse, and (silently) stop. Notice what it deliberately does not do — there's no call that persists text anywhere, and no write that sets status to ready. That absence is the scope boundary from the Background section made concrete in code: a good file's variable named text gets logged (its length, not its content) and then simply falls out of scope when the function returns, exactly as the implementation guide specifies. A bare Python exception raised anywhere in here (a Firestore outage, a Storage timeout) is not caught locally — it's allowed to propagate up to the consumer, which is the signal that distinguishes "this document is bad" (handled here, ends in failed) from "our infrastructure is broken" (handled one layer up, ends in the dead-letter queue).

8. The broker-aware shell: consumer.py

ingest-worker/src/ingest/consumer.py (new)

Everything else in the worker is deliberately broker-agnostic; this file is the one place that actually imports pika and talks AMQP. Its on_message callback is short enough to read as a single decision:

def on_message(channel, method, properties, body) -> None:
    try:
        envelope = json.loads(body)
        run_ingest_job(envelope)
        channel.basic_ack(delivery_tag=method.delivery_tag)
    except Exception:  # infra failure / bad JSON / bug
        log.exception("infra failure; dead-lettering delivery")
        channel.basic_nack(delivery_tag=method.delivery_tag, requeue=False)

Recall that run_ingest_job already converts every document-level problem (bad magic bytes, a corrupt parse) into a Firestore failed write and a clean return — so if it returns normally at all, the message gets acknowledged (basic_ack), full stop, regardless of whether the document itself turned out good or bad. It's only an actual raised exception — malformed JSON, Firestore or Storage unreachable, an honest-to-goodness bug — that falls into the except branch, which nacks with requeue=False. Given the dead-letter exchange declared at connect time, that single flag is what routes the message to doc.ingest.dead instead of looping it back into doc.ingest forever. The code comments are blunt about the resulting invariant: a message that ends up in the dead queue always means the worker or infrastructure malfunctioned, never that a user uploaded a bad file — so an operator watching that queue's depth is watching a pure alarm signal, not user behavior.

One more detail worth surfacing: channel.basic_qos(prefetch_count=1) combined with manual acknowledgment is what makes crash recovery work at all. If the worker process dies partway through a job, the unacknowledged message simply stays claimed by nobody once the connection drops, RabbitMQ redelivers it (to this worker on restart, or another one), and — as covered in the Intuition section — claim_for_processing sees the record already at processing and returns RERUN rather than treating the redelivery as an error.
