Background

For beginners: queues, magic bytes, sandboxes, transactions

You already know how the Next.js half enqueues an envelope. Before diving into the Python side, it's worth pinning down four ideas the worker leans on heavily — skip this subsection if any of them are old hat.

Message queues and workers. A message queue like RabbitMQ sits between two processes that don't need to know about each other. A producer drops a small message onto a named queue; a consumer pulls messages off that queue one at a time and does work. The upside is decoupling — the producer (Next.js, in this repo) doesn't block on the consumer (the Python worker) being up, fast, or even alive. If the consumer crashes mid-message, a well-behaved queue can redeliver that message once the consumer reconnects, so no work is silently dropped — but this means the consumer has to be able to handle the same message twice without corrupting anything. That property is called idempotency, and a good chunk of this worker's design exists purely to guarantee it.

Magic bytes. File formats often begin with a fixed, distinctive byte sequence so that a program can identify the format without trusting the file extension. A real PDF always begins with the ASCII bytes %PDF-; a ZIP-based format (like a modern .docx) begins with PK\x03\x04; the old Microsoft Compound File Binary format (legacy .doc, .xls, .ppt) begins with the byte sequence D0 CF 11 E0 A1 B1 1A E1. Checking these first few bytes — "sniffing the magic number" — is a cheap, dependency-free way to catch a file that's been mislabeled or is simply garbage, before you spend real work trying to parse it as if it were valid.

Subprocess sandboxing. Parsing an untrusted file — one a stranger uploaded to your server — is dangerous in the same process as the rest of your application: parser libraries have parsed enough malformed input over the years to be reasonably hardened, but "reasonably hardened" is not the same as "provably safe," and a bad file can still hang a parser in an infinite loop or exhaust memory. The standard defense is to run the parser in a separate child process with a hard timeout. If the child hangs, crashes, or takes too long, the parent simply kills it and moves on — the parent process, which is doing the important job of staying alive to consume the next message, is never at risk.

Firestore transactions. Firestore lets you read a document, decide what to do based on what you read, and write back — all atomically, as a single transaction. If two processes run a transaction against the same document concurrently, Firestore guarantees only one of them "wins": the other's transaction is retried against the now-updated document. This is exactly the primitive you need to answer the question "has anyone already started processing this document?" without a race condition.

Where the Python worker picks up

One sentence of recap, since you already know this half: finalizeUpload writes a Firestore record at status uploaded and then publishes a tiny envelope — exactly {"uid": "...", "docId": "..."}, nothing else, never file bytes — onto the durable queue doc.ingest.

From here on, everything lives in ingest-worker/, a standalone Python 3.12 project with its own src/ingest/ package and its own pytest suite. It's a separate OS process, typically running in its own Docker container with no published ports — the broker envelope is its only door in. The worker re-reads everything it needs from Firestore using just the uid/docId pointer; the envelope is deliberately "pointer-only" so it can never disagree with the record it points at.

Repo invariant this ticket refines
The worker's only writes are Firestore status transitions. Storage is strictly read-only to it — a rejected or corrupt file is flagged failed, never deleted. This is also why it's safe, in dev, to point the worker's Firestore at an emulator while it still reads real GCS bytes: an emulated-Firestore worker can never touch production storage.

The status vocabulary is the same DocStatus you already know from the frontend: pending → uploaded → processing → ready | failed. This ticket owns exactly two of those arrows — uploaded → processing and processing → failed. Reaching ready is deliberately out of scope (that's ticket #5): a successfully parsed file in this codebase ends at processing, with its extracted text held in memory and then simply discarded when the worker moves on to the next envelope.

Intuition: three gates a document must pass

Once you strip away the infrastructure, the whole worker is one function — run_ingest_job(envelope) — pushing a single document through three gates in strict order. Each gate can only make the outcome worse, never better: a document that fails gate one never reaches gate two.

Gate 1 — Claim Firestore transaction: is anyone already working on this doc? Am I allowed to?
↓
Gate 2 — Precheck Do the first bytes on disk actually match the contentType Firestore says this file is?
↓
Gate 3 — Sandboxed parse Can a real parser extract text from this file inside 20 seconds, in a disposable child process?

All three gates live inside run_ingest_job — the broker never sees any of this.

Let's walk a toy example through all three gates, using the exact fixtures the test suite uses: uid = "user-a", docId = "doc-1".

Case A — a well-formed PDF

Firestore has a record at users/user-a/documents/doc-1 with status: "uploaded" and contentType: "application/pdf". The object at users/user-a/documents/doc-1 in Storage really does start with %PDF- and is a valid one-page PDF.

GATE 1: CLAIMED

Transaction sees uploaded, flips it to processing, stamps claimedAt. Proceed.

GATE 2: PASS

data.startswith(b"%PDF-") is true for the declared contentType. Proceed.

GATE 3: PASS

Child process runs pypdf, extracts text, exits 0 inside the 20s budget. Record stays at processing.

Good file: ends at processing, not ready — text is held in memory and discarded.

Case B — text bytes mislabeled as a PDF

Same starting record, but Storage actually holds the bytes b"just text pretending to be a pdf" under contentType: "application/pdf" (this is one of the repo's own test fixtures, test_mismatched_bytes_fail_and_object_is_retained).

GATE 1: CLAIMED

Same as before — claiming doesn't know or care what the bytes are.

GATE 2: REJECT

data.startswith(b"%PDF-") is false. precheck() returns False before any parser ever runs.

GATE 3: never reached

mark_failed() flips the record straight to failed. The Storage object is left alone — only the flag changes.

Mismatches are caught cheaply, in-process, before spending a subprocess spawn on them.

Case C — valid header, garbage body

Storage holds b"%PDF-1.7" + <a few KB of random bytes>. The magic number is genuinely correct, so gate 2 passes — but the file isn't a real PDF, so pypdf will choke on it.

GATE 1: CLAIMED

Unaffected.

GATE 2: PASS

The header genuinely says PDF — precheck can't see past the first few bytes.

GATE 3: REJECT

The child process raises inside pypdf; sandbox.py turns that into a ParseError. mark_failed() runs.

This is exactly why parsing has to be a second, independent gate — magic bytes alone can't prove a file is well-formed.

Case D — the same envelope, delivered twice

This is the case the whole "claim" design exists for. Imagine the worker finishes Case A, but crashes (power loss, OOM-kill, whatever) a split second before it would have sent the acknowledgment back to RabbitMQ. The broker, having never heard an ack, redelivers the exact same {uid, docId} envelope to the next worker that connects.

uploaded →CLAIMED processing →redelivery finds it already processing RERUN

Second delivery re-claims (refreshing claimedAt) and reprocesses from scratch — safe, because the only side effect either run has is a status write.

Compare that to a redelivery arriving after the document reached ready or failed — those are terminal, so the claim function reports SKIP and nothing happens. That asymmetry — processing reprocesses, ready/failed never regress — is the whole idempotency story in one sentence, and it's enforced by a single Firestore transaction you'll meet in the code walkthrough.

Code walkthrough

The package is ingest-worker/src/ingest/, and the modules read almost exactly in dependency order — each one imports only the ones before it. We'll walk them in that order: configuration, claiming, prechecking, sandboxed parsing, the orchestrator that ties them together, and finally the thin broker shell around all of it.

Configuration and the canonical path

ingest-worker/src/ingest/config.py

config.py reads everything from environment variables and initializes firebase_admin exactly once, lazily, the first time anything asks for a Firestore client or Storage bucket: 

def firebase_app():
    global _app
    if _app is None:
        bucket = os.environ["FIREBASE_STORAGE_BUCKET"]  # required; fail loudly
        _app = firebase_admin.initialize_app(
            credentials.ApplicationDefault(), {"storageBucket": bucket}
        )
        log.info(
            "firebase initialized: firestore=%s storage=%s bucket=%s",
            os.environ.get("FIRESTORE_EMULATOR_HOST") or "REAL",
            os.environ.get("STORAGE_EMULATOR_HOST") or "REAL",
            bucket,
        )
    return _app

That boot log is a small but deliberate safety net: because a misconfigured FIRESTORE_EMULATOR_HOST is exactly the kind of mistake that would otherwise fail silently (every envelope just looks ABSENT and gets acked away), the very first log line the worker ever prints says plainly which Firestore and which bucket it resolved.

ingest-worker/src/ingest/paths.py

Right next to it sits the smallest file in the package — and one of the most important, because of what it's not allowed to do: 

def document_storage_path(uid: str, doc_id: str) -> str:
    """4th caller of the ONE canonical path formula.

    Mirrors documentStoragePath() in doculyze/_lib/database.tsx — the signer,
    the finalize verify, and the Firestore record all use the same shape. Do
    not derive paths any other way.
    """
    return f"users/{uid}/documents/{doc_id}"

This is a straight reimplementation of the same formula you already know from _lib/database.tsx — Python and TypeScript can't literally share a function, so the discipline is social: this is the one place the path gets built on the Python side, and every other module calls it rather than formatting the string itself.

Claiming a document (the replay rules)

ingest-worker/src/ingest/firestore_status.py

This module is the answer to "what happens when the same envelope arrives twice." It exposes one enum and two functions. The enum names the four possible outcomes of trying to claim a document: 

class Claim(Enum):
    CLAIMED = "claimed"  # uploaded -> processing, proceed to parse
    RERUN = "rerun"      # already processing (crash-after-claim redelivery) -> re-parse
    SKIP = "skip"        # ready/failed -> ack, no-op (no regression)
    ABSENT = "absent"    # pending or missing -> log warning, ack

claim_for_processing wraps the read-decide-write sequence in a single @firestore.transactional function, so the whole thing is atomic even if two workers are racing: 

@firestore.transactional
def txn(tx) -> Claim:
    snap = ref.get(transaction=tx)
    if not snap.exists:
        return Claim.ABSENT
    status = snap.get("status")
    if status == "uploaded":
        tx.update(ref, {"status": "processing", "claimedAt": firestore.SERVER_TIMESTAMP})
        return Claim.CLAIMED
    if status == "processing":
        # Guarded re-claim, not a read-only peek: keeps contention behavior
        # correct when consumers multiply.
        tx.update(ref, {"claimedAt": firestore.SERVER_TIMESTAMP})
        return Claim.RERUN
    if status in ("ready", "failed"):
        return Claim.SKIP
    return Claim.ABSENT  # "pending" or unknown

The subtle design choice here is that RERUN still performs a write — it refreshes claimedAt — rather than just reading the status and returning. With exactly one consumer and prefetch 1 (more on that in the consumer section), nothing is actually racing today, so that write looks unnecessary. But it costs nothing, and it means that if this worker is ever scaled out to multiple consumers, the transaction already serializes them correctly — no redesign needed later, per the commit's design-grill notes.

The companion function is a one-liner that never touches Storage: 

def mark_failed(db, uid: str, doc_id: str) -> None:
    """processing -> failed, flag-only. Never touches Storage (bytes retained)."""
    _doc_ref(db, uid, doc_id).update({"status": "failed"})

The test suite (test_firestore_status.py) nails down exactly the behavior you'd expect: calling claim_for_processing twice on the same uploaded record yields CLAIMED then RERUN, never two CLAIMEDs; and both ready and failed always come back SKIP — a resolved record can never be knocked backwards by a stray redelivery.

The magic-number precheck

ingest-worker/src/ingest/precheck.py

precheck() is a pure, dependency-free function — no I/O, no Firestore, no subprocess — that takes the record's stored contentType (the one the Next.js upload flow already derived from the file extension) and the raw bytes downloaded from Storage, and answers a single yes/no question: do these bytes actually look like that type?

contentTypeCheck
application/pdfstarts with %PDF-
docx (OOXML)starts with PK\x03\x04 and the zip's entries include [Content_Types].xml
application/msword (.doc)starts with the CFB signature D0 CF 11 E0 A1 B1 1A E1
text family (plain/json/js/ts/md/html/css/xml)decodes as clean UTF-8, no NUL byte, and doesn't start with any of the binary signatures above
anything elseFalse — an unknown contentType should never have been signed in the first place

The docx check is worth lingering on, because PK\x03\x04 alone would be too weak — a .docx, a .zip, and a .xlsx all share that same four-byte ZIP signature. So the check goes one step further and actually opens the zip's central directory (using Python's built-in zipfile module — still dependency-free) and confirms a specific entry, [Content_Types].xml, is present. That file is a required part of every valid OOXML package, so its presence is a much stronger signal than the raw ZIP magic bytes alone. 

def _zip_has_entry(data: bytes, name: str) -> bool:
    try:
        with zipfile.ZipFile(io.BytesIO(data)) as z:
            return name in z.namelist()
    except zipfile.BadZipFile:
        return False
Known, accepted limitation
The CFB signature is shared by every legacy Office format — .doc, .xls, and .ppt all start with the same eight bytes. So a spreadsheet renamed to end in .doc sails through precheck() and only gets caught later, when antiword chokes on it and gate 3 fails instead. The design accepts this: the precheck is a cheap first filter, not the only filter — the parser is always the second, more expensive gate behind it.

Parsing inside a subprocess sandbox

ingest-worker/src/ingest/parsers.py, sandbox.py, parse_entry.py

Three small files cooperate here, and it's worth seeing how they fit before reading each one:

Parent process (the worker)
  • sandbox.py::run_parser_sandboxed()
  • never imports pypdf / python-docx itself
  • spawns the child, writes bytes to its stdin
  • waits up to PARSE_TIMEOUT_S (default 20s)
  • reads text back from stdout
bytes in →

← text or exit≠0
Child process (disposable)
  • python -m ingest.parse_entry <parser_name>
  • parsers.py does the actual pypdf / python-docx / antiword work
  • any exception → caught, printed to stderr, exit 1
  • killed outright if it exceeds the timeout

The parent's contract with the child never changes: bytes in on stdin, extracted text out on stdout, non-zero exit or a timeout means "this file is bad."

sandbox.py is the parent-side half — it shells out via subprocess.run and converts every failure mode into one exception type: 

def run_parser_sandboxed(parser_name, object_bytes, timeout_s=None) -> str:
    if timeout_s is None:
        timeout_s = parse_timeout_s()
    try:
        proc = subprocess.run(
            [sys.executable, "-m", "ingest.parse_entry", parser_name],
            input=object_bytes,
            capture_output=True,
            timeout=timeout_s,
            env=_child_env(),
        )
    except subprocess.TimeoutExpired as exc:
        raise ParseError(f"{parser_name} timed out after {timeout_s}s") from exc
    if proc.returncode != 0:
        raise ParseError(
            f"{parser_name} exited {proc.returncode}: "
            f"{proc.stderr.decode('utf-8', 'replace')[:300]}"
        )
    return proc.stdout.decode("utf-8", errors="replace")

Both a hang (caught as TimeoutExpired) and a crash (non-zero exit code) collapse into the exact same ParseError — the caller one layer up (job.py) doesn't need to know or care which one happened; either way, the document is bad and gets marked failed.

parse_entry.py is the child's own entrypoint — deliberately tiny, because it's the part of the codebase that actually touches untrusted bytes with real parsing libraries: 

def main() -> int:
    parser_name = sys.argv[1]
    data = sys.stdin.buffer.read()
    try:
        text = PARSERS[parser_name](data)
    except Exception as exc:  # any failure is a parse failure
        print(f"parse failed ({parser_name}): {exc}", file=sys.stderr)
        return 1
    sys.stdout.buffer.write(text.encode("utf-8"))
    return 0

And parsers.py holds the actual extraction logic plus a small dispatch table (parser_for()) that maps a canonical contentType to a parser name — a pure lookup, safe to call from anywhere, since it never touches file bytes itself: 

_PARSER_BY_TYPE = {
    "application/pdf": "pdf",
    DOCX_TYPE: "docx",
    "application/msword": "doc",
    **{ct: "text" for ct in TEXT_FAMILY},
}

Three of the four parsers are short and unsurprising — pypdf for PDFs, python-docx for docx, a plain UTF-8 decode for the text family. The fourth, .doc via antiword, needs a small workaround worth calling out, because it breaks the otherwise-uniform "bytes in on stdin" model: 

def _parse_doc(data: bytes) -> str:
    # antiword reads a file PATH, not stdin — write the bytes to a temp file
    # inside this sandboxed child; it dies with the child.
    tmp = tempfile.NamedTemporaryFile(suffix=".doc", delete=False)
    try:
        tmp.write(data)
        tmp.close()
        proc = subprocess.run(["antiword", tmp.name], capture_output=True)
        if proc.returncode != 0:
            raise RuntimeError(f"antiword exited {proc.returncode}: {proc.stderr[:200]!r}")
        return proc.stdout.decode("utf-8", errors="replace")
    finally:
        os.unlink(tmp.name)

antiword is a command-line tool that only knows how to read a file path, not standard input, so this function writes the bytes to a temporary file first. Two details matter here: delete=False plus a manual os.unlink() in a finally block (rather than the more common with tempfile.NamedTemporaryFile() as tmp: pattern) exists because Windows won't let a second process — antiword — open a file that's still held open by the first. And because this all runs inside the sandboxed child, the temp file's entire lifetime is scoped to that disposable subprocess; it's gone the moment the child exits, sandboxed one level deeper via a nested subprocess.run call to antiword itself.

Tying it together: run_ingest_job

ingest-worker/src/ingest/job.py

This is the module every test in ingest-worker/tests/ ultimately calls, and it's also literally the entire pipeline from the intuition section, laid out top to bottom with no broker in sight: 

def run_ingest_job(envelope: dict) -> None:
    uid, doc_id = envelope["uid"], envelope["docId"]
    db = firestore_client()

    decision = claim_for_processing(db, uid, doc_id)
    if decision in (Claim.SKIP, Claim.ABSENT):
        log.info("skip/absent for %s/%s: %s", uid, doc_id, decision.value)
        return
    # CLAIMED or RERUN: the record is now `processing`.

    snap = db.collection("users").document(uid) \
             .collection("documents").document(doc_id).get()
    content_type = snap.get("contentType")
    data = storage_bucket().blob(document_storage_path(uid, doc_id)).download_as_bytes()

    if not precheck(content_type, data):
        mark_failed(db, uid, doc_id)  # object retained (flag-only)
        return

    try:
        text = run_parser_sandboxed(parser_for(content_type), data)
    except ParseError as exc:
        mark_failed(db, uid, doc_id)  # object retained
        return

    # Good file: ENDS at `processing` (ticket #5 takes it to `ready`).
    log.info("parsed %s/%s: %d chars (held in memory only)", uid, doc_id, len(text))

Notice what this function does not do: it never raises for a bad document. A precheck rejection and a parse failure both return normally, after quietly writing failed. The only way run_ingest_job raises is an actual infrastructure problem — Firestore or Storage being unreachable, for instance — and that distinction (document-level failure returns cleanly; infrastructure failure raises) is exactly what the consumer shell uses next to decide between an ack and a nack.

The pika consumer shell

ingest-worker/src/ingest/consumer.py

Everything above this point is broker-agnostic — you could call run_ingest_job from a cron job, a CLI, or a test, and it wouldn't know the difference. consumer.py is the one module that actually knows RabbitMQ exists, and it's kept deliberately thin: 

def on_message(channel, method, properties, body) -> None:
    try:
        envelope = json.loads(body)
        run_ingest_job(envelope)
        channel.basic_ack(delivery_tag=method.delivery_tag)
    except Exception:  # infra failure / bad JSON / bug
        log.exception("infra failure; dead-lettering delivery")
        channel.basic_nack(delivery_tag=method.delivery_tag, requeue=False)

Read this against what you just learned about run_ingest_job: a bad file (precheck or parse failure) already returned normally, so control reaches basic_ack — the message is done, successfully, even though the document ended up failed. Only something run_ingest_job couldn't handle itself — malformed JSON, a Firestore/Storage outage, an unexpected bug — falls into the except branch, which nacks with requeue=False. Because the queue was declared with a dead-letter exchange, that nack routes the message to doc.ingest.dead instead of looping it back onto the live queue — a poison message gets one shot, then waits for a human, rather than spinning forever. 

channel.basic_qos(prefetch_count=1)
channel.basic_consume(queue=queue, on_message_callback=on_message, auto_ack=False)

prefetch_count=1 plus manual acking (auto_ack=False) is what makes Case D from the intuition section — the crash-mid-job scenario — actually safe in practice. RabbitMQ only ever hands this worker one unacknowledged message at a time; if the process dies before acking, the broker notices the connection drop and redelivers that same message once a consumer reconnects. That redelivery lands right back in claim_for_processing, which by now sees the record sitting at processing and returns RERUN instead of blowing up or double-processing something already finished.

Finally, declare_topology asserts the exact same queue, exchange, and binding shape that the Node producer declares on its side: 

def declare_topology(channel, queue: str) -> None:
    channel.exchange_declare(exchange=DLX, exchange_type="direct", durable=True)
    channel.queue_declare(queue=DEAD_QUEUE, durable=True)
    channel.queue_bind(queue=DEAD_QUEUE, exchange=DLX, routing_key=queue)
    channel.queue_declare(
        queue=queue, durable=True, arguments={"x-dead-letter-exchange": DLX}
    )

RabbitMQ hard-fails an assertQueue/queue_declare call if the arguments don't match an already-declared queue of the same name — so if the Node and Python sides ever drift on this shape, you find out immediately and loudly, rather than via some subtler runtime mismatch later.
